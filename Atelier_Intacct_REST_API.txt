 Sage Intacct API REST
L’API REST Sage Intacct permet d’accéder aux données et aux fonctions de Sage Intacct (facturation, achats, trésorerie, etc.) depuis des applications
externes. Les échanges se font en HTTP/JSON ; l’accès est sécurisé par OAuth 2.0.



Points clés :
      •   Authentification : deux flux — Client Credentials (machine-à-machine, token sans utilisateur) et Authorization Code (connexion utilisateur
          via navigateur).
      •   Consultation : Query (object, fields, filtres, tri, pagination) et Export (même logique, résultat en PDF, CSV, etc.).
      •   CRUD sur les objets : GET (liste ou détail), POST (création), PATCH (mise à jour partielle), DELETE (suppression), sur des ressources du type
          /objects/{application}/{object}.
      •   Traitement en masse : Bulk (jobs asynchrones : envoi d’un fichier, suivi par jobId, téléchargement du résultat).
      •   Requêtes groupées : Composite (plusieurs appels GET/POST/PATCH/DELETE en un seul POST).

  OAuth 2.0 : Flux Client Credentials (Machine à
  machine)
- Le flux Client Credentials est utilisé pour un accès direct à l'API sans intervention de l'utilisateur.
- Pour l'utiliser, l’ID Client doit être autorisé et lié à un utilisateur Web Services dans la configuration de société.


- Pour demander un token, envoyez une requête POST au point de terminaison suivant avec les paramètres requis, incluant le username
- Format username UTILISATEUR_WEB_SERVICES@ID_SOCIÉTÉ|ENTITÉ pour cibler une entité précise, ou omettez l'entité pour un accès global au
niveau général (Top Level).




                                                                                                            token_type : Type de jeton (Bearer).
                                                                                                            access_token : Clé d'accès API.
                                                                                                            refresh_token : Jeton de renouvellement.
                                                                                                            expires_in : Durée de validité (6h).

  OAuth 2.0 : Flux Authorization code
 Quand un utilisateur réel doit se connecter à Intacct via votre application (navigateur, app mobile), on utilise le flux Authorization Code : l’utilisateur
 s’identifie une fois sur Sage Intacct, accepte d’autoriser votre app, et vous recevez un code à usage unique pour obtenir un token à son nom. Les appels
 API sont donc faits pour ce compte utilisateur, et non pour un compte webservice « machine » comme en Client Credentials.

Utilisez le service Model pour obtenir les détails d'une ressource (champs interrogeables, types de données, valeurs autorisées et
relations), éléments utilisables dans vos requêtes pour tous les types d'objets, services et flux de travail.


Points d'entrée (Endpoints) disponibles :
      •   Résumé global : /services/core/model (Affiche toutes les ressources de la version actuelle).
      •   Ressource spécifique : /services/core/model?name=company-config/department (Modèle complet pour un objet précis).
      •   Version spécifique : /services/core/model?name=projects/task&version=v1 (Modèle complet selon une version d'API).
      •   Par type et version : /services/core/model?version=v1&schema=true&type=workflow (Toutes les ressources d'un type précis).

 Le Service Query : Structure d'une Requête 1/3
Le service Query permet d'extraire des données précises en définissant la structure de la
réponse et les critères de sélection.
Définition de la Cible et des Champs
1.   Endpoint : /services/core/query
2.   Objet (object) : Type d'objet à interroger (ex: accounts-payable/vendor).
     Pour les objets personnalisés, utilisez le format platform-apps/nsp::<name>.
3.   Champs (fields) : Liste des champs à retourner.Simples : id, name. Liés : vendor.id (accès aux objets
     parents).
4.   Agrégats : sum:amount, count:id, min, max, avg.

 Lecture (GET) 1/3
La méthode GET permet de consulter les ressources existantes, soit en collection, soit par enregistrement spécifique.
Récupération de Données (GET)
      •   Format d'Endpoint : Utilise la structure /objects/{application}/{object} (ex: accounts-receivable/invoice).
      •   List (Collection) : Retourne une liste simplifiée (clés, IDs, liens) de tous les enregistrements pour l'exploration ou les tests.
      •   Get Single (Détails) : Extrait l'intégralité des champs d'une ressource spécifique en ajoutant sa clé unique à l'URL : /{object}/{key}.
      •   Métadonnées (ia::meta) : Présentes pour confirmer le succès (totalCount) et gérer la pagination (next, previous) dans le cas des listes.
      •   Contenu de Réponse : Fournit un tableau de références pour les listes ou l'objet complet détaillé pour une lecture individuelle.
      •   PS (Important) : Le mode List comporte une limitation majeure car il ne supporte pas les paramètres de pagination ou de filtrage (ex: start),
          l'utilisation du Query Service est impérative.

 Création de Données (POST) 1/2
La méthode POST permet de soumettre un nouvel enregistrement vers une ressource spécifique pour l'ajouter à la base de données.
     •   Format d'Endpoint : Utilise la structure racine de l'objet /objects/{application}/{object}.
     •   Corps de la Requête (Body) : Nécessite un format JSON incluant les champs obligatoires, tels que les dates, les montants et les objets liés (ex:
         customer).
     •   Réponse de Succès (201) : Le serveur retourne l'objet ia::result contenant uniquement les informations d'identification et de navigation :
         l'ID, la Key système et le lien HREF vers la nouvelle ressource.

 Mise à jour de Données (PATCH) 1/3
La méthode PATCH permet de mettre à jour partiellement un enregistrement existant identifié par sa clé, sans remplacer l’intégralité de la ressource.
      •   Format d'Endpoint : Utilise la structure racine de l’objet avec la clé : /objects/{application}/{object}/{key} (méthode PATCH).
      •   Corps de la Requête (Body) : Format JSON partiel contenant uniquement les champs à modifier ; les propriétés absentes sont ignorées et ne
          modifient pas les valeurs existantes.
      •   Réponse de Succès (200) : Le serveur retourne l’objet ia::result contenant les données mises à jour ou une confirmation de l’opération.

 Requêtes en lot (Batch)
Permet de traiter plusieurs enregistrements d'un même type d'objet en un seul appel. Le traitement est synchrone (réponse immédiate) et limité à
500 enregistrements.
Format d’endpoint
      •   Lecture : GET /objects/{object}/194,195,310
      •   Suppression : DELETE /objects/{application}/{object}/1,2,3 (IDs séparés par des virgules dans l'URL)
      •   Création/Modification : POST ou PATCH /objects/{application}/{object}
Corps de la requête (Body, Utilisé uniquement pour POST et PATCH)
      •   Format : Tableau d'objets JSON [ { ... }, { ... } ].
      •   Spécificité PATCH : La key doit être incluse dans chaque objet du body (et non dans l'URL).


Gestion Atomique (Header) : X-IA-API-Param-Transaction: true
Si un seul élément échoue, toute l'opération est annulée (Rollback).
Réponse de succès (200 / 204 / 207)204 No Content pour un DELETE groupé réussi.207 Multi-Status si le résultat est mixte (succès/échecs partiels).

 Requêtes en masse (Bulk) - soumission du job
Le service Bulk permet de soumettre une opération en masse (create, update, etc.) de façon asynchrone. L’API enregistre le job et retourne un
identifiant (jobId) à utiliser pour suivre le traitement.
      •   Format d’endpoint : POST /services/bulk/job/create (requête multipart).
      •   Corps de la requête (Body) : Requête en form-data (multipart), avec deux parties :
            1.   ia::requestBody (type Texte) : un objet JSON contenant objectName, operation, jobFile, fileContentType, et optionnellement
                 callbackURL. La valeur de jobFile doit être le même nom que la deuxième clé.
            2.   file, type Fichier : un fichier .json contenant un tableau d’enregistrements à traiter (ex. [{ "id": "vendor1", "name": "..." }, ...]).
      •   Réponse de succès (201) : Le serveur retourne ia::result contenant le jobId, utilisé ensuite pour interroger le statut et, une fois terminé,
          télécharger le résultat.

 Requêtes en masse (Bulk) – statut et téléchargement
Une fois le job soumis, le statut s’obtient par un GET sur l’endpoint de statut. Quand le job est terminé, le même endpoint permet de télécharger le
fichier résultat en passant le paramètre download=true.
      •   Format d’endpoint : GET /services/bulk/job/status avec les paramètres de requête jobId (obligatoire) et download (optionnel, à true pour
          récupérer le fichier résultat).
      •   Corps de la requête (Body) : Aucun. Les requêtes GET n’ont pas de corps.
      •   Réponse de succès (200) : Le serveur retourne ia::result avec le statut du job (ex. status, percentComplete). Si download=true et que le job
          est terminé, la réponse contient le fichier résultat (contenu ou pièce jointe selon l’API).

 Composite – Envoi de plusieurs requêtes en un seul
 appel
Le service Composite permet d’envoyer plusieurs requêtes (GET, POST, PATCH, DELETE) en un seul appel HTTP.
L’API exécute les sous-requêtes dans l’ordre et renvoie un tableau de réponses (une par sous-requête). Une sous-requête peut exposer un
resultReference pour que les suivantes utilisent son résultat.
      •   Format d’endpoint : POST /services/core/composite (corps JSON = tableau de sous-requêtes).
      •   Corps de la requête (Body) : Un tableau JSON. Chaque élément contient : method (GET, POST, PATCH, DELETE), path (chemin de la
          ressource, ex. /objects/accounts-payable/vendor), et optionnellement body (pour POST/PATCH), resultReference (identifiant pour
          réutiliser le résultat), headers (ex. Idempotency-Key).
      •   Réponse de succès (200) : Le serveur retourne ia::result (tableau : une entrée par sous-requête, chacune avec ia::result, ia::meta, ia::status)
          et ia::meta global (totalCount, totalSuccess, totalError).
